# Scan/range study

From the repository root, install the pinned Bun dependencies (`bun install --frozen-lockfile`), install Chromium (`bunx --bun playwright install chromium`), and build the regular renderer (`bun scripts/build-wasm.mjs`, requires the repo's Rust toolchain). On Windows:

```powershell
.\bench\studies\scans\run.ps1                   # optional: -Bun C:\path\to\bun.exe
bun bench/studies/scans/summarize.ts            # rebuild results/scans-study.md
```

The wrapper holds `Local\LeafviewBrowserStudy2026` throughout generation and measurement. The results replace `results/scans-study.json` only after all conditions pass. On other platforms use `bun bench/studies/scans/run.ts` with exclusive use of the benchmark machine. JPEGs and PDFs exist only in process memory.

**Inputs.** Seeded 144 dpi letter-size inventory scans (1224×1584, JPEG quality .76) have paper noise, dark ink, text, row rules and changing lot numbers. The independent packets embed one unique image per page; the shared controls reference the very same first JPEG from every page. The first visible scan therefore matches for all four PDFs, excluding a small vector marker that identifies the fixture and page. The PDFs have non-linearized, ordered objects and a conventional trailing xref. The pinned Chromium JPEG encoder, Windows Arial and browser rasterization affect byte reproducibility; compare fixture hashes in the JSON.

**What changes.** Unmodified Leafview uses its production worker's full GET. Both PDF.js conditions use the same viewer host and its PDF.js adapter, with a benchmark-only injection of loading flags: `disableStream` and `disableAutoFetch` both true, `rangeChunkSize=65536`, and `disableRange` true/false. This isolates range behavior inside PDF.js. The 206 comparator **is not implemented in Leafview**. Each condition is a fresh, `no-store` browser context in a reused browser process. The host is loaded; engine module imports, workers, parsing, mounting the page list and rendering are timed. Each mode occupies each order position once per fixture over three repetitions. Opening one packet ends at the host's first rAF after inserting its page-one canvas; the marker and both dark/light pixels inside the scan must match. This is a render-complete frame marker, not a display hardware timestamp.

**Transfer accounting.** The HTTP/1.1 loopback server serves the PDFs with identity encoding, `Content-Length`, `Accept-Ranges: bytes`, and valid `Content-Range` on 206s. Renderer assets use precomputed gzip. Each response waits 40 ms before headers, then competes for one shared 50 Mbit/s byte clock in 32 KiB writes; simultaneous fetches share capacity. Range-on includes the initial 200 request even when PDF.js cancels it, counting only body bytes actually written. Each sample records PDF-only and all timed responses, plus the individual Range headers, declared lengths, status and encoded body bytes written by the frame. No extrapolation from advertised length. Timing is correlated via browser/server epoch-based performance clocks on the same machine. Kernel/socket queues and cancellation races can separate server writes from client reads. HTTP headers, TLS, retransmission, jitter, congestion control, and the preloaded shell are outside the byte totals. The JSON records first/last body-write times for checking achieved bandwidth: for a long single-response transfer divide `(encodedBytes - 32768) * 8` by `(lastBodyMs - firstBodyMs) * 1000` for decimal Mbit/s.

**Interpretation.** This is cold-document first preview, not scrolling throughput, warm cache behavior, or time to load all pages. Many short range reads incur extra request delays; a larger shared file need not benefit simply because it contains many pages. The comparison is specific to these documents' object order, JPEG density, range size and link. Neither these synthetic scans nor three local samples represent a production PDF distribution or a tail-latency estimate.
